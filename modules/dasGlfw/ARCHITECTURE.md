# modules/dasGlfw - architecture

The contract every architecture doc follows is `ARCHITECTURE_COMMON.md` (repo root).

## 1. Charters

- `src/dasGLFW.main.cpp` - the hand-bound part of the binding: the callback chain, the synthetic
  event API, the real-input mute, the per-frame canvas reconcile on `glfwPollEvents`, the virtual
  key table behind `glfwGetKey`, and the web-only queries (canvas box, device pixel ratio, touch
  list, touch device, fullscreen). Everything else in `src/` is generated by `bind/bind_glfw.das`;
  a function this file hand-binds is in that binder's skip list.
- `src/glfw_emscripten_stubs.c` - the GLFW 3.4 entry points emscripten's JS GLFW lacks.
- `src/glfw_emscripten_cursor.c` - `glfwSetInputMode` for a browser without Pointer Lock.
- `src/glfw_emscripten_touch.c` - every finger on the canvas, kept in JavaScript and polled.
- `dasglfw/glfw_live.das` - the window and frame lifecycle for a daslang-live app, and the
  synthetic mouse and keyboard drivers the live host speaks.
- `dasglfw/glfw_touch_pad.das` - on-screen controls for a keyboard game on a touch device.
- `tests/` - node tests of the web glue's JavaScript bodies, and the pad's windowless dastest.

## 2. Mechanisms

### 2.1 The touch list {#touch-list}

Emscripten's GLFW turns the first finger on the canvas into the left mouse button and drops
every other finger. The touch glue keeps its own list: listeners on the canvas record each
finger's identifier and position, in the same coordinate space emscripten gives the mouse, and
the poll that runs at the top of `glfwPollEvents` commits the frame's view of it. The first poll
installs the listeners and reports nothing; every later poll commits the pending flags. A finger's
`began` and `ended` flags hold for exactly one frame after the poll, so a tap that starts and
ends between two frames is still seen once, with both flags set. The program reads the list
with scalar queries (`glfw_touch_count`, `glfw_touch_x`, ...) because a scalar return needs no
pointer marshalling under the 64-bit wasm ABI. On the desktop the list is empty and
`glfw_is_touch_device` is false; a touch device is one whose primary pointer is coarse, or that
has touch points and no hover; under `--touch-pad` the desktop feeds the left mouse button as one
finger, so a pad mapping can be tried without a phone. The EM_JS bodies sit behind plain C entry points, because an
EM_JS symbol resolves only inside its own translation unit; the binding declares those C names
and calls them.

### 2.2 Virtual keys {#virtual-keys}

A game polls `glfwGetKey` and never installs a key callback, so the synthetic key events the
live host posts through the callback chain cannot reach it. The binding hand-binds
`glfwGetKey` over a table of virtual keys: a key the table holds reads as pressed, everything
else falls through to GLFW. The table is one per process, not per window, and the pad clears it
whole at the top of every frame, so a reload that empties the pad's own list cannot leave a key
pressed. The on-screen pad writes that table and the game's polling code is
unchanged. The ImGui backend does not poll `glfwGetKey`, so a virtual key never doubles into
ImGui.

### 2.3 The on-screen pad {#touch-pad}

The pad is immediate mode: each frame the game declares its zones, buttons, d-pad, swipe and
tap between `pad_begin_frame` and `pad_end_frame`, in window fractions so one layout fits every
screen. A zone claims the fingers inside it and holds its key for the frame; the swipe, the tap
and the drag axis see only unclaimed fingers, which is why they are declared after the zones.
`pad_begin_frame` releases the previous frame's keys, so a tap is a one-frame press and a hold
is a held key, the same edge and hold semantics the keyboard gives. The pad draws with its own
small GL program over the finished frame, so it works in every game's renderer and in every
shell. A game that plays sideways declares `pad_prefer_landscape`; in a portrait window the pad
draws a scrim with a landscape frame, holds no keys, and the game writes the words under it. A
test injects fingers and reads the held keys back, with no window.
